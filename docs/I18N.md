# Project Nexus internationalization

Status: canonical Phase 0 policy, 2026-10-07. Initial locales **zh-CN** and **en-US** are equally supported. This document owns user-facing terminology; [DESIGN_SYSTEM](DESIGN_SYSTEM.md) owns layout and typography. No translation resources or application code are created in Phase 0.

## 1. Translation architecture

Use i18next with react-i18next in the frontend. Native/Rust code returns stable domain codes and safe typed parameters, not English sentences requiring reverse translation. Keep release translation resources bundled and available offline; no runtime remote translation dependency.

Future resource organization is by locale and feature: `locales/{zh-CN,en-US}/{common,navigation,home,agents,models,providers,extensions,system,settings,health,diagnostics,repair,errors}.json`. This is a design path, not an instruction to scaffold now. Provider forms can live in their own namespace while Models remains the primary navigation item.

Use semantic stable keys, e.g. `agents:actions.launch`, `health:status.ready`, `repair:plan.affectedAgents`, `errors:config.concurrentChange`. Keys express meaning, never source-language sentences or numeric positions. Reuse common keys only when grammatical context and meaning truly match; keep distinct Cancel installation and Cancel repair messages when consequences differ.

No ordinary user-facing strings in React components, CSS generated content, charts, placeholder text, tooltips, validation, accessibility attributes, toasts, or menus. Product names, exact model IDs, paths, technical literals and user-entered labels are data; do not translate them. Use complete sentences with named interpolation; do not concatenate fragments. Do not render untrusted translations/parameters as HTML. React text escaping remains enabled; rich messages use a small audited component interpolation set.

## 2. Locale selection and persistence

On first launch with no explicit preference, inspect OS language preferences using a native read-only facility. If the selected system language is any Chinese language tag (`zh` and its region/script variants), choose `zh-CN`; otherwise choose `en-US`. This fulfills the initial Chinese-system rule; it does not claim Traditional Chinese localization. Offer a visible language selector immediately.

Persist an explicit user choice in local preferences and honor it across restarts. “Follow system / 跟随系统” remains an explicit selectable mode; in this mode recompute when the OS language changes. Explicit zh-CN/en-US does not change when the OS does. Switching language updates all mounted views and future native dialog text without restart, without resetting in-progress operations or unsaved forms. Operation records store message codes/parameters, so history renders in the current language.

An open native confirmation dialog retains its language until dismissed rather than rewriting consent mid-dialog; subsequent dialogs use the new choice. This narrow dialog behavior does not require an application restart.

Fallback chain: resolved supported locale → en-US → safe generic localized error with diagnostic code. Missing keys fail development/CI parity checks; production logs the missing key identifier without user content and never intentionally shows a raw key. A missing critical confirmation translation blocks release. Locale resource failure uses a minimal bundled fallback so cancellation/recovery remain usable.

## 4. Formatting and language mechanics

Use `Intl.DateTimeFormat`, `Intl.NumberFormat`, and locale-aware relative-time/plural facilities available in the chosen runtime. Store UTC instants, render in the user's configured/system timezone, and expose an exact timestamp/timezone for diagnostic evidence. Relative “just now” must not hide stale evidence. Prefer unambiguous absolute time in confirmations and history. Never hardcode US date order, decimal separators, or thousands separators.

Use i18next plural variants with a numeric `count` and complete phrases. English distinguishes one/other (with deliberate zero messaging when useful); Chinese uses natural measure words and does not imitate English plural suffixes. Example intent: “1 Agent needs attention” / “3 Agents need attention”; Chinese “有 1 个 Agent 需关注” / “有 3 个 Agent 需关注”. Counts are real data, not decorative summaries.

Chinese prose uses full-width Chinese punctuation；technical paths, model IDs, command examples, URLs, and version strings preserve ASCII punctuation exactly. Use a single space between Chinese text and a Latin technical word/number when natural (“检查 Agent 状态”), without inserting spaces inside copied identifiers. English UI uses sentence case. Avoid unexplained acronyms and untranslated idioms; do not use machine translation output as approved copy.

Numbers with units use localized patterns, not string concatenation. Preserve full model IDs and versions without number formatting. Future cost values must carry currency, source and time; an unavailable price is unknown, never zero. Do not implement usage/cost UI in MVP.

## 5. Validation and native error contract

Native error envelope concept: `code`, typed `params`, `retryable`, `operationId`, optional redacted `evidenceId`. The frontend maps known codes to feature/error keys; no localization key supplied by an untrusted process is executed. Unknown code uses a generic localized explanation plus safe diagnostic identifier. Parameters cannot contain secrets or raw upstream body text.

Localize form constraints before submission and authoritative Rust validation after submission consistently. Example `provider.invalid_url` identifies the field and accepted protocol without echoing a credential-bearing URL. `config.concurrent_change` explains that the original changed and requires refreshing the plan. `credential.store_locked` distinguishes locked storage from missing authentication.

Technical upstream error strings appear only as redacted quoted evidence under a translated summary. Never dump an English Rust stack trace as the main dialog. Native-owned confirmation uses the same approved message catalog or a generated native catalog from the same source, with parity checks; Rust remains owner of the facts and authorization. Exact catalog packaging is a Phase 1/4 integration decision, not two independently maintained translations.

## 6. Bilingual layout, accessibility, and tests

Translation is part of design. Allow content-driven widths, wrapping labels/help, long Provider names, and 40% English expansion fixtures. Test sidebars, tabs, tables, dialogs, forms, tooltips, empty states, loading/errors, toasts, logs, installation/repair summaries and Model compatibility. Critical consent text is never ellipsized. Truncated technical values have a focusable full-value disclosure/copy action.

All accessible names, descriptions, progress announcements, errors, sort labels, and shortcut descriptions are localized. A row action includes its Agent name to avoid repeated indistinguishable “Launch” buttons. Set document language live. Keep screen-reader announcement frequency independent of polling and locale switching.

Future CI checks key parity, unused/missing keys, interpolation parameter parity/types, plural forms, accidental hardcoded user strings, and complete critical confirmations. Manual acceptance uses a native speaker for each locale, OS-specific screen readers, narrow desktop and zoom, both themes, and live language switching during a safe operation. Pseudo-localization is a development test aid, not a third supported locale. No language support is “complete” until these checks run on the implemented UI.
